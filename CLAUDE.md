# CLAUDE.md — Project Rules

This file defines **hard rules** for anyone (human or Claude Code agent) working in this
repository. It is enforced guidance, distinct from `SKILL.md` (day-to-day conventions/how-to)
and `ARCHITECTURE.md` (the full design — the source of truth this file summarizes into rules).
When in doubt, `ARCHITECTURE.md` wins; this file exists so the rules that must never be broken
are visible without reading the whole design document.

## Project Purpose

An **AI Agentic Web Automation Testing Framework**: Playwright-based browser test automation,
structured around the Page Object Model, extended with 12 specialist agents (Orchestrator,
Requirement Analysis, Product Discovery, Test Design, Test Data, Automation Generation,
Execution, Failure Analysis, Self-Healing, Gap Analysis, Regression, Reporting) as defined in
`ARCHITECTURE.md`. All 12 agents exist as real, working code
(`.framework/agents/*.js` + `.claude/skills/*/SKILL.md`) and run end-to-end in **DRY-RUN /
SYNTHETIC mode** (`npm run framework:dry-run`) against clearly-labeled synthetic fixtures and
the pre-approved public demo target — never against a real customer application, which requires
its own separately-approved onboarding (see README.md "Real Application Onboarding").

## Technology Stack

JavaScript (Node.js, CommonJS) · Playwright + `@playwright/test` · Playwright CLI · Playwright
MCP · GitLab MCP (read-only) · Page Object Model · Claude Code · `SKILL.md`-defined agent
skills. Full rationale in `ARCHITECTURE.md`.

## Coding Standards

- CommonJS (`require`/`module.exports`), matching `package.json`'s `"type": "commonjs"`.
- No inline selectors in test files — selectors live in page objects (`pages/`) only.
- No business logic in `utils/` or `BasePage` — those stay generic and reusable.
- Keep functions small and single-purpose; don't add abstractions for hypothetical future
  needs (matches this project's general engineering conventions).

## JavaScript-Only Rule

This project is JavaScript, not TypeScript. No `.ts`/`.tsx` files, no type-annotation syntax, no
TypeScript compiler/tooling. `// @ts-check` + JSDoc comments (already used in `pages/*.js`) are
the only type-checking mechanism, and are optional, not required. Introducing TypeScript would
be a distinct architecture decision, not a casual addition.

## POM (Page Object Model) Rules

- One class per page/major component, extending `BasePage`.
- `BasePage` contains **only** generic, reusable browser/page functionality (navigation, waits,
  reload, title) — never business-specific logic or a specific page's selectors.
- Locators are class properties on the page object, role/label-first
  (`getByRole`, `getByLabel`), never raw CSS/XPath unless nothing stable exists.
- Every page object gets a fixture entry in `fixtures/*.fixture.js`; tests obtain page objects
  from a fixture, never construct them inline.
- Full detail: `SKILL.md` conventions section; design rationale: `ARCHITECTURE.md` Section D.

## Playwright Rules

- **Playwright Test** (`@playwright/test`) is the execution engine for all automated test runs.
- **Playwright CLI** (`npx playwright test [--project=] [--grep=] [--shard=]`) is the standard
  way to run/filter the suite locally and in CI.
- **Playwright MCP** is for **live, interactive** work only — discovery, locator validation,
  failure diagnosis. It is never used to execute the test suite itself; CI results must never
  depend on an interactive MCP session (`ARCHITECTURE.md` Section E).

## Test Naming Conventions

- Spec files: `<feature-or-flow>.spec.js`, one feature/flow per file.
- Test titles describe observable behavior (`'home page has expected title'`), not
  implementation details.
- One behavior/assertion focus per test.

## Folder Ownership

| Folder | Owner / who may write here |
|---|---|
| `pages/` | Page-object authors. Once the Self-Healing Agent exists, it may **only** touch locator-level lines here — never anything else in the repo. |
| `fixtures/` | Fixture wiring for page objects into `test`. |
| `tests/` | Spec files. Never edited by the Self-Healing Agent. |
| `utils/` | Generic, application-agnostic helpers only (data generation, auth foundation, API client/token adapters). No business logic. |
| `.claude/skills/<agent>/SKILL.md` | One file per specialist agent, defining its contract. Deviates from `ARCHITECTURE.md` Section 5's originally proposed `.skills/` path — `.claude/skills/` is the actual Claude Code skill-discovery convention; flagged as a documentation discrepancy, not a control-flow change (see the Phase implementation report). |
| `.framework/lib/`, `.framework/schemas/`, `.framework/agents/` | Framework runtime code and schemas — tracked in git. Human-reviewed changes only. |
| `.framework/runs/`, `reports/` | Generated per run, git-ignored. Never hand-edited — always regenerated by running the pipeline. |
| `playwright.config.js`, `.mcp.json`, CI config | Human-reviewed changes only; no agent (including Automation Generation or Self-Healing) may modify these. |

## Security Rules

- No secret (password, token, API key, connection string) is ever hardcoded in code, tests,
  config, comments, or committed to git.
- Test Data/Discovery activity targets only a dedicated **non-production** test environment —
  never production.
- Playwright storage-state files (`.auth/*.json`) are treated as live session secrets.

## Secret-Management Rules

- `.env` is never committed. `.env.example` documents variable **names** only, with empty
  values — see that file.
- `.gitignore` must always contain `.env`, `.env.*`, `!.env.example`, and `.auth/`. Do not
  remove or narrow these entries without an explicit reason recorded here.
- Credentials are read from environment variables only (`utils/auth.js`'s
  `getRoleCredentials`) — never from a hardcoded fallback value.
- GitLab PAT (`GITLAB_PERSONAL_ACCESS_TOKEN`) and any application credential live only in
  environment variables / CI secret variables.

## MCP Rules

- **Playwright MCP**: interactive discovery/authoring/diagnosis only (see Playwright Rules
  above). Currently connected.
- **GitLab MCP**: must remain **`GITLAB_PERMISSION_MODE=readonly`** in `.mcp.json` until
  `ARCHITECTURE.md` Phase 9 is explicitly approved. No agent or automated process may change
  this value — only a human, editing `.mcp.json` directly, with a recorded decision.
- No agent is granted unrestricted GitLab write access, ever, regardless of phase — write
  access, when it eventually arrives, is narrow and MR-based (Section H), never direct pushes.

## Git Rules

- This repository's `.git` is scoped to this project folder only.
- No destructive git operation (`reset --hard`, `push --force`, `clean -f`, history rewrite)
  without explicit human approval for that specific action.
- No automatic commits — a human approves each commit explicitly.
- Never commit `.env`, `.auth/`, or anything matching a secret pattern; if `git status` after a
  broad `git add` shows anything unexpected, stop and inspect before committing.

## Environment Safety Rules

- **Production execution is blocked by default** (`.framework/lib/environment-safety.js`,
  wired into `playwright.config.js` via `globalSetup`). This only activates once a real,
  non-placeholder `BASE_URL` is configured — it never affects the preserved demo smoke test.
- Once a real `BASE_URL` exists, execution is blocked unless `TEST_ENVIRONMENT=non-production`
  is explicitly set. An optional `PRODUCTION_HOSTS` denylist hard-blocks specific hostnames
  regardless of that setting.
- The framework must never autonomously execute against production — this is enforced in code,
  not only documented here.

## Agent Safety Rules

All 12 specialist agents exist as real, working code
(`.framework/agents/*.js`, `.claude/skills/*/SKILL.md`).

- Each specialist agent is single-responsibility and stateless — no memory between runs;
  everything it needs is an input artifact, everything it produces is an output artifact.
- No agent invokes another agent directly. All sequencing goes through the Orchestrator; all
  handoffs go through the file-based artifact store (`ARCHITECTURE.md` Section N).
- Each agent's tool/file access is scoped to exactly what its spec (Sections 3–14) grants —
  never broader "just in case."
- Nothing runs unattended in CI except the Execution Agent (pure Playwright CLI) until a human
  has separately approved otherwise (`ARCHITECTURE.md` Section P, Decision 4).

## Self-Healing Restrictions

(Implemented and unit-tested — see `tests/framework/self-healing-safety.spec.js`. Finalized
2026-08-25, Decision 1 — see `ARCHITECTURE.md` Section 9 and Section H for full detail. In the
current dry-run implementation, `self-healing.schema.json` additionally hard-codes
`dryRun`/`realFileWritePerformed`/`mrOpened`/`mergeApprovedByHuman` to fixed safe values, so no
real file write, MR, or merge is even representable yet, let alone possible.)

- **Never**, at any confidence level, for any reason — including being asked to "make the test
  pass" — modify an assertion, expected business outcome, validation logic, or test intent.
- May only write to files under `pages/`, and even then, high-confidence auto-healing is
  limited to **locator-level changes and similarly low-risk structural fixes** — nothing
  broader is eligible for auto-apply.
- Every change that reaches "apply," at any confidence, must: produce a diff → re-run the
  affected test → confirm assertions unchanged → write an audit record → open a GitLab MR
  (never push directly to a protected branch) → wait for human review before merge. This
  applies **even at high confidence** — auto-apply only ever means the local diff + re-run
  happen automatically; merge approval never does.
- Never acts on a failure not already classified `selector-drift` by the Failure Analysis
  Agent — it cannot see (and therefore cannot "fix away") a real regression.

## Human Approval Requirements

Consolidated gates (full list: `ARCHITECTURE.md` Section Q):

1. Any requirement flagged ambiguous
2. First discovery run against a new target URL
3. Test case sets touching a high-risk category: **Payments, PII/Sensitive Data, User Account
   Deletion, Financial Transactions, Authentication/Authorization** (finalized 2026-08-25)
4. New data-generation strategy needing a new credential/scope
5. First-time creation of a new page object file; any new spec before merge
6. Every self-healing proposal at Medium confidence (blocking)
6a. Merging any self-healing MR — **including High confidence**
7. Any failure not classified `selector-drift`
8. Switching `GITLAB_PERMISSION_MODE` away from `readonly`
9. Enabling any generative agent to run unattended in CI
10. Publishing any report/comment externally to GitLab

## Requirement-to-Test Traceability Rules

(`ARCHITECTURE.md` Section A. Implemented — see `.framework/lib/manifest.js` and
`tests/framework/traceability.spec.js`.)

- Every generated test case traces to a requirement ID via the run's `manifest.json`. No
  orphan generated test without a linked requirement now that the agentic layer is active.
- The current demo (`tests/home.spec.js`, `pages/HomePage.js`) predates the agentic layer and
  is exempt as pre-framework scaffolding — it is not linked to any requirement and should not
  be mistaken for real coverage of a real application.
- The Orchestrator is the sole writer of `manifest.json`; no other agent updates it directly.
